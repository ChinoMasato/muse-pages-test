02なぜGitHubに上げるのか

なぜGitHubに上げるのか

一番大きいのは、自分のAIエージェントとコードを共有できること。

⭐ 最大のメリット ─ 自分のAIエージェントとつながる

自分のAIエージェントがリポジトリ全体を読んで、今のコードを前提に直す・足す・調べる。「作る → 上げる → AIエージェントに読ませて直す → また上げる」のAI駆動開発のループが回り始める。

🛠 先生からも見てもらえる

chinomasato と y1389 を登録すると、千野と吉田先生の両方から開発状況を見てもらえる。開発もポートフォリオ作りもシームレスになる。

📁 ポートフォリオの材料になる

企画書・プロトタイプ・作る過程が1つのリポジトリに揃う。就活で見せる「作品」と「過程」がここに溜まる。

上げる理由は初級と同じ。ただし中級では見る先生が2人になる。
03プランナー志望へ ─ 中級の核心

プランナー志望も、
企画書だけで終わらない

今の時代は、企画書だけでなく、動くプロトタイプまで作って検証しましょう。

📝 企画書は「仮説」だ

「こうすれば面白いはず」は、紙の上ではまだ仮説でしかない。面白いかどうかは、実際に動かして、遊んでみて初めて分かる。企画書で止まると、仮説が合っていたかどうかを一生確かめられない。

🎮 プロトタイプで検証する
  • コアの遊びだけを、粗くてよいので動く形にする
  • 自分で遊ぶ＋誰かに遊んでもらう
  • 「思った通りだった／違った」を言葉で残す
  • 結果を企画書に反映して直す
🤖 AIがある今、言い訳はできない

コードが専門でなくても、AIエージェントと一緒に作ればプロトタイプは作れる時代になった。だからプランナーこそ「書ける」だけでなく「動かして確かめられる」ことが強みになる。

プランナー志望の提出物 ＝ 企画書 ＋ 動くプロトタイプ ＋ 検証メモ。この3点セットで1つだ。
千野の指示をそのまま核心に置く：プランナー志望も企画書だけでなく動くプロトタイプまで作って検証する。他の志望も同じ検証の考え方を使う。

05記録が残る、ということ

記録が残る、ということ

試行錯誤まで残るから、アピールに漏れがない。

GitHubに上げ続けると、コミットとして開発の過程そのものが残る。企画の変更も、プロトタイプの失敗も、検証して直した履歴も、全部たどれる。

✅ 記録があると
  • 「何をアピールすればいいか」をAIと一緒に履歴から拾える
  • 企画→検証→修正の判断が、証拠として残る
  • ポートフォリオや面接で、過程まで含めて語れる
⚠ 記録がないと
  • 完成品しか残らず、過程の工夫は思い出せなくなる
  • アピールポイントの漏れが出る
  • AIも過程を見られないので、支援が的外れになりやすい
全部をAIにゆだねなくてよい。任せるところは任せ、自分で判断するところは自分でやる。重要なのは、開発の記録をAIが把握できる状態にしておくことだ。
初級の「記録」と「AIとの付き合い方」を中級向けに統合。検証の履歴まで残すことが中級のポイント。
06手順1 ─ リポジトリを作って上げる

手順1 ─ リポジトリを作って上げる

作って、最新版を上げて、目で確認する。

📮 手順
  1. GitHubで新しいリポジトリを作成する（名前は作品が分かるものに）
  2. 企画書（PDFなど）と、動くプロトタイプ（プロジェクト一式／遊べる形）を上げる
  3. READMEに「遊び方」と「検証したいこと」を書く
  4. 手元の最新版を上げる（古い版や、一部だけのファイルはNG）
  5. ブラウザでリポジトリを開いて、ファイルが揃っているか目で確認する

詰まったら止まったままにしない。エラー文をそのまま控えて、早めに先生に声をかける。

「GitHubに中級課題のリポジトリを作って、企画書とプロトタイプを上げたいです。手順を1つずつ教えてください。プロトタイプは企画のコアの遊びが確かめられる最小の形で作りたいです」
